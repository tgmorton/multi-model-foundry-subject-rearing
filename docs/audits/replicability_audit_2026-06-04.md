## 1. Replicability scorecard

|---|---|---|

## 2. Critical findings (G2 breaks — these block the clean re-run)

The three critical findings below all share **one root cause** (the DataLoader has no dedicated, epoch-keyed RNG and resume does not fast-forward) plus **one amplifier** (kernel nondeterminism makes even fresh restarts non-byte-identical). They must be fixed together; the RNG redesign in §4 is the unifying fix.

### C1. Resume re-runs the in-progress epoch from batch 0 with a fresh, wrongly-seeded shuffle (no fast-forward)

- **Mechanism.** `load_checkpoint` restores `global_step` and `epoch` only (`checkpointing.py:322-323`); `training_state.pt` stores **no within-epoch batch index** (`checkpointing.py:127-141`). The loop does `for epoch in range(self.epoch, …)` (`loop.py:180`) and builds a fresh `data_iter = iter(self.dataloader)` (`loop.py:209`) at the top of every epoch. The inner `while True` (`loop.py:211-219`) breaks only on `StopIteration` or `global_step >= train_steps` — there is no skip of consumed micro-batches. So a checkpoint saved mid-epoch E (stored as `epoch=E`, `global_step=S`) resumes by re-entering epoch E at batch 0, retraining the pre-crash slice, and then terminating ~one partial epoch early because `global_step` keeps climbing from S to `train_steps`.
- **Compounding.** The re-entered epoch is not even the *same* permutation: `data.py:447-456` is `DataLoader(shuffle=True)` with **no `generator=`**, so RandomSampler draws its permutation from the global torch CPU RNG at `iter()` time. On resume that RNG is restored to the *mid-epoch save* state (`checkpointing.py:330-334`), which differs from the state at the original epoch's start. The resumed epoch therefore trains a *different* data order than the uninterrupted run ever saw.
- **Why it fires routinely.** With ~97 anchors over 30 epochs and front-loaded log-spaced anchors (0,1,2,4,8,…) over ~128k chunks, almost no resume-capable anchor lands on an epoch boundary, and pods are preempted often. Verifier confirmed via the schedule that of the 19 resume-state anchors, 17 happen to be exact epoch boundaries but the 2 earliest mid-epoch ones (ep7 waypoint, midpoint) plus a 1-optimizer-step rewind at boundary anchors still diverge.
- **Evidence.** `loop.py:115-116,180,184,209,211-219`; `checkpointing.py:127-141,322-334`; `trainer.py:439,470-475,521-526`; `data.py:447-456`.
- **Fix.** (a) Deterministic per-(seed, epoch) DataLoader generator (see §4) so the re-entered epoch's order is reproducible from epoch start; **and** (b) fast-forward the first resumed epoch by the restored within-epoch offset, *or* restrict resume-state checkpoints to epoch boundaries only. Persist an explicit within-epoch micro-batch index in `training_state.pt` (additive, back-compatible: old checkpoints default to 0 = legacy behavior) rather than recomputing `(global_step % steps_per_epoch)*grad_accum`, because the per-epoch optimizer-step count is floor-not-ceil (trailing micro-batches that never reach an accumulation boundary drop without a step, `loop.py:416/441`), so the modulo arithmetic can be off by a step.
- **Tradeoffs.** Fast-forward costs I/O-only wall-time (up to ~one epoch of `next()` calls, no compute) — acceptable versus a wrong trajectory. Epoch-boundary-only resume is simpler but discards the early/mid waypoints' restartability. Pre-fix checkpoints cannot be made byte-exact retroactively — state this in methods.

### C2. Fresh-restart "deterministic overwrite" of early checkpoints is NOT byte-identical (FA2 atomicAdd backward)

- **Mechanism.** `production_agent.py:278-282,304-308` restarts a pre-waypoint run from step 0 and re-saves the early weights-only anchors, asserting "the same seed re-walks the same trajectory and overwrites the same anchors." This holds **only for checkpoint-0** (saved before any optimizer step — pure `set_seed` init). For any step>0 anchor it is false: FA2 is hard-coded (`trainer.py:205`), its backward accumulates dQ/dK/dV via fp32 `atomicAdd` (run-to-run nondeterministic on the same GPU), fused AdamW (`trainer.py:298-300`) and the AMP GradScaler (`loop.py:74`) add more, and nothing sets `torch.use_deterministic_algorithms` (zero matches repo-wide). After hundreds of nondeterministic backward passes the re-walked checkpoint-512 differs in the low bits.
- **False confidence.** The one validated restart was on the LSTM, which does not route through FA2 attention — i.e. the one arch where the bug *doesn't* bite. GPT-2/BERT (the attention archs) were never exercised on this path.
- **Evidence.** `production_agent.py:278-282,304-308`; `trainer.py:153-154,205,298-300`; `loop.py:74`; `utils.py:27-34`; repo-wide grep (zero `use_deterministic_algorithms`/`CUBLAS_WORKSPACE_CONFIG`).
- **Fix.** Recommended **(A)**: document that fresh-restart overwrite is byte-identical only for checkpoint-0 and statistically equivalent (not bitwise) for step>0 anchors; gate the overwrite so it never overwrites a step>0 anchor a resume could already have consumed (the existing `stale_steps[-1] < first_resume_anchor` guard at `production_agent.py:295` already enforces this — extend the comment). Option **(B)** (true determinism — `use_deterministic_algorithms(True, warn_only=True)`, `CUBLAS_WORKSPACE_CONFIG=:4096:8`, leave FA2 for SDPA) is materially slower and would undercut the FA2-motivated GPU pool. Note: transformers 4.41.2 does **not** plumb flash-attn's `deterministic=` kwarg, so "make FA2 deterministic" is not available without leaving FA2.
- **Tradeoffs.** (A) is documentation-only and safe; it accepts that early overwritten anchors are statistical, not bitwise — fine because they are weights-only (no resume consumes them past the guard). (B) costs ~10–30% throughput and a GPU-pool rethink.

### C3. BERT MLM masking RNG is not restored on resume (worker-process stream)

- **Mechanism.** `MaskedLMDataCollator._mask_tokens` (`data_collators.py:204,211,217,221`) calls `torch.bernoulli`/`torch.randint` with **no explicit generator**, so masking draws from the ambient torch RNG of the *worker* process. On the production pods `num_workers` auto-resolves to ≥1 (`data.py:434-441`), so the collator runs in a worker seeded by `_worker_init_fn` from `torch.initial_seed()` (`data.py:40-43`). Workers are non-persistent (`persistent_workers` unset → respawn every epoch). `training_state.pt` restores only main-process RNG (`checkpointing.py:330-334`) — the worker base seed it depends on is re-derived from the (restored, mid-epoch) main stream, which does not match what the uninterrupted run's epoch would have used. A resumed BERT run therefore produces a different (chunk → mask) pairing for the remainder of training, silently. This is a **separate** stream from C1's shuffle: fixing the sampler generator does not fix the collator.
- **Scope correction.** This is **BERT-only** (one of the five archs). The auditor's broader claim that CausalLM *data order* also breaks through the worker mechanism is **refuted** — shuffle runs in the main process and its RNG *is* restored (see §5). Severity downgraded from "critical, all-arch" to **critical for BERT, scoped**.
- **Evidence.** `data_collators.py:204,211,217,221`; `data.py:40-43,434-441,447-456`; `checkpointing.py:330-334`; `production_agent.py:313-338` (resume path applies to BERT). Note CausalLM collator (`data_collators.py:165-169`) uses no RNG at all.
- **Fix.** Give `MaskedLMDataCollator` an explicit `torch.Generator` seeded from a **stable** function of `(random_seed, epoch, batch_index)` and pass `generator=g` to every `bernoulli`/`randint`. Thread `epoch` in via a settable attribute updated in `loop.py` before each `iter()`; use a monotonic batch counter. These are CPU ops on CPU tensors, so a CPU generator suffices (no CUDA-determinism entanglement). See §4.
- **Tradeoffs.** A few lines of plumbing; no throughput cost. Do not use Python's builtin `hash((seed,epoch,batch))` — it is `PYTHONHASHSEED`-salted per process and `PYTHONHASHSEED` is never set, so it would itself be nondeterministic; use `seed*K + epoch*K2 + batch` or `hashlib`.

## 4. The RNG redesign (one coherent proposal)

The current pipeline has **no dedicated RNG streams** — every random consumer draws from the single global torch RNG, entangling data order, masking, and dropout with arch-specific model-init draw counts and with resume timing. Replace this with explicit, purpose-salted generators, all derived from one base seed via a **stable** (non-`hash()`) derivation.

**Base derivation helper** (new, e.g. `model_foundry/rng.py`):
```
def derive_seed(base_seed, purpose, epoch=0, batch=0):
    # stable across processes/pods — NO Python builtin hash()
    h = hashlib.blake2b(f"{base_seed}|{purpose}|{epoch}|{batch}".encode(), digest_size=8)
    return int.from_bytes(h.digest(), "little") & 0xFFFFFFFFFFFFFFFF
```

| Stream | Derivation | Purpose-salt? | Arch-salt? | Lands in | After fix, honest claim per arch |
|---|---|---|---|---|---|
| **Weight init** | global torch RNG, seeded by `set_seed(base_seed)` re-called immediately before `_initialize_model` | n/a | n/a (intentionally) | `trainer.py:455` (move/duplicate `set_seed`) + new G3 test | Bitwise-identical init across the 5 conditions for fixed (arch, seed) — **asserted**, not accidental. Kernel-independent. |
| **Data order (shuffle)** | `g_data = torch.Generator(); g_data.manual_seed(derive_seed(base_seed, "data_order", epoch))` — reseeded each epoch, passed as `generator=` to the DataLoader; recreate/reseed in `loop.py` before each `iter()` | yes | **NO** (PI decision — recommend no salt) | `data.py:447` + `loop.py:209` | Data order is a pure function of (seed, epoch), restart-stable, and **identical across arches** at equal seed (a property the paired design wants; currently arch-dependent). |
| **MLM masking (BERT)** | `g_mask = torch.Generator(); g_mask.manual_seed(derive_seed(base_seed, "mlm_mask", epoch, batch_idx))` passed into every `bernoulli`/`randint` | yes | implicit via base_seed | `data_collators.py:204,211,217,221` + epoch/batch threaded from `loop.py` | Masking is reproducible, fresh-per-epoch, and independent of worker-spawn timing → restart-stable. CPU generator (CPU tensors) — no CUDA entanglement. |
| **Dropout (GPT-2 / BERT / LSTM / Mamba)** | CUDA philox stream, seeded by `set_seed`; **already saved/restored** in `training_state.pt` (`checkpointing.py:330-334`) | n/a | n/a | no change needed | Restart-stable already (CUDA RNG is checkpointed). Only the *kernel* (not the RNG) is nondeterministic — see below. |
| **Worker `__getitem__`** | `_worker_init_fn` should derive from `derive_seed(base_seed, "worker", epoch, worker_id)` rather than `torch.initial_seed()` | yes | implicit | `data.py:40-45` | Decoupled from the global stream; only relevant if any map-side randomness is added later (currently none). |

**Determinism claim each arch can honestly make after the RNG redesign alone (RNG streams fixed, kernels unchanged):**

- **GPT-2 (small/medium/large):** data order, masking-N/A, dropout, and init are all reproducible and restart-stable → **trajectory matches on resume up to FA2 atomicAdd backward noise**. Same-GPU = **statistical replication** (bit-repro only if `training.deterministic`: SDPA + `use_deterministic_algorithms` + TF32 off).
- **BERT large:** as GPT-2, **plus** masking now restart-stable (closes C3). Same-GPU = statistical (SDPA backward + atomicAdd reductions).
- **LSTM:** init/data/dropout reproducible; cuDNN RNG backward is on the deterministic path (`cudnn.deterministic=True` is set) → **can credibly claim bitwise same-GPU** once `use_deterministic_algorithms` + `CUBLAS_WORKSPACE_CONFIG` are added and validated (cuDNN may raise for some hidden sizes — validate the cell). Does not use FA2.
- **Mamba 370M:** init/data/dropout reproducible; the fused selective-scan/conv backward is nondeterministic and invisible to the determinism guard → **statistical replication only**, no bitwise path without switching to the (different, slower) pure-PyTorch block.

**The RNG redesign is necessary but not sufficient for G2:** it makes the resumed epoch's order/masks reproducible, but C1's within-epoch **fast-forward** (or epoch-boundary-only resume) is still required so the resumed run doesn't re-train the epoch prefix.

## 5. Refuted findings (kept here so they stay dead)

- **GradScaler scaler-state overwrite corrupts resume** — *Refuted.* The fresh-restart overwrite only rewrites weights-only (scaler-less) early anchors below `min(resume_state_steps)`; no resume ever reads a scaler from an overwritten anchor (guarded at `production_agent.py:295`). Already-enforced invariant, not a defect.
- **Worker RNG makes every epoch use the SAME shuffle/mask pattern** — *Refuted.* Misreads PyTorch: with `persistent_workers=False`, each epoch's `iter()` draws a NEW `base_seed` from the main global RNG, so `torch.initial_seed()` in the worker differs every epoch; masks already vary per epoch. Shuffle runs in the main process, not workers.
- **cuDNN LSTM backward breaks G1 now** — *Refuted.* `cudnn.deterministic=True` IS set (`trainer.py:154`), which puts cuDNN RNN on the deterministic path — the finding concedes this mid-text. The "raises under `use_deterministic_algorithms`" half is hypothetical (that flag is never set) and version-unverifiable on torch 2.5.1.
- **MLM masking finding tagged critical/all-effects** (data_collators #1) — *Refuted as written.* Its headline ("masks byte-identical across every epoch") rests on the same PyTorch misreading above; the genuine resume-only divergence is the scoped BERT break already captured in **C3**. Its `hash()`-based fix is itself nondeterministic (`PYTHONHASHSEED`).
- **Shuffle entangled with arch-init defeats cross-arch matched-data comparisons** (data_collators #3) — *Refuted as a G1 break.* Its own text concedes data order is deterministic per fixed arch, so G1 is not broken; the "matched data order across arches" requirement is invented (the study requires matched *tokens seen*, not matched order). The real residual (entanglement fragility) is the same known shuffle finding, fixed by §4.
- **Env snapshot S3 best-effort makes outage runs un-auditable** — *Refuted.* `git_commit` and `config_hash` are durably written to `checkpoint-*/metadata.json` on the same CephFS PVC as the weights (`checkpointing.py:152-189`), independent of S3. The only at-risk artifact is the pip-freeze manifest, itself largely recoverable from the pinned commit's `requirements.txt`. Residual is minor, not moderate.
- **`nvidia-smi -L` omits driver version, recorded nowhere** — *Refuted.* `Trainer._save_environment_snapshot` (`trainer.py:345-392`, called at `:506`) writes full `nvidia-smi` (driver + CUDA version) and `torch.version.cuda` to a durable PVC-symlinked logs path. Driver provenance exists; it is just not a queryable column (covered by the GPU-model finding's promote-to-field fix).

## 6. Fix bundle for the clean re-run (ordered, smallest-diff-first)

1. **Re-seed before model init + add G3 assertion test.** Duplicate `set_seed(config.random_seed)` at `trainer.py:455`; add a test building the same (arch, seed) under two conditions asserting bitwise-equal initial `state_dict`. *(Makes G3 structural.)*
2. **Set `PYTHONHASHSEED` in the pod env** (launcher YAML), not at runtime. *(Hygiene; prerequisite for any stable tuple-hash derivation.)*
3. **Pin the wave's git SHA.** Launcher resolves `git rev-parse HEAD` once, clones that SHA (wire up the existing `docker-entrypoint.sh:36-41` path), injects `GIT_REF`. *(Unifies code state; G4.)*
4. **Pin the image by digest + record it.** Use the CI `:<short-sha>`/`@sha256` in all production YAMLs and `DOCKER_IMAGE`; add `docker_image_digest` to the registry; pin Dockerfile extras + base image. Exact-pin the `requirements.txt` range deps to live `pip freeze`. *(G4; behaviorally neutral.)*
5. **Record GPU model per run.** `NODE_NAME` via downward API; pass `torch.cuda.get_device_name(0)` + `node_name` into `register_run_start`. *(G4; enables G5 partition.)*
6. **Add `corpus_content_hash` to the cache key and run record.** Reuse the COMPOSE_MANIFEST sha256 or stream `.train` bytes. *(G4; one-time cache recompute.)*
7. **RNG redesign — dedicated generators** (§4): per-(seed, epoch) DataLoader generator (`data.py:447` + `loop.py:209`) and per-(seed, epoch, batch) MLM-collator generator (`data_collators.py`). *(Closes the cross-arch entanglement and is the prerequisite for resume determinism.)*
